# 示例：智能多式联运方案求解器如何贯穿设计阶段

> 仅演示文档写作结构。以下内容是常见设计示例，**不能在未获得项目确认时当作项目最终功能要求**。

D0：来源登记可研报告、需规、已确认功能反馈、演示系统页面。记录范围为“方案求解”而非整套运输组织。

D1：角色（经本项目确认的管理人员）希望针对粮食运输需求，比较铁路、公路、水运或组合路线，依据成本、时效和运输方式偏好选择方案。

D2：FLOW-001 运输需求→求解参数→候选方案→比选→方案确认→后续供需/运力匹配。二级菜单保留“方案管理”“方案求解”“线路运价”等经确认业务功能；方案详情宜做页面下钻。

D3：MOD-001 方案求解：输入为始发地、目的地、货物/载重、时间要求、偏好/排除方式、价格区间；输出为候选路线、区段节点、费用分项与 ETA，说明每项价格与时间口径。遇到不可行时返回明确原因，而非空结果。

D4：PAGE-001 求解页面：主工作区为参数与地图；候选方案列表紧邻关键路径；筛选和比选不会生成无依据统计小卡；原型具备空载/无方案/超时状态。

D5：独立 HTML 原型允许用“示意路线 + 模拟运价”展示交互，但必须以醒目标识清楚区分；不能声称高德货车收费能力已接入。

D6：审核每条 REQ 有模块、页面、原型入口和 AC，并检查交通运输数据实际来源、完整运价规则和用户审批。
