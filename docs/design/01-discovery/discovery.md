## 1 本节点结论

产品面向庆阳新能源重卡运输与补能协同，以管理员桌面端和司机手机 H5 构成操作闭环。九模块47项业务功能全部纳入本轮设计；另覆盖九项非功能需求以及运营与汇报数据一致性，共57条需求。

用户已明确：从零设计，实际运营与汇报展示并重；2026-10-13 批准 D0 并要求逐节点推进；本轮又确认司机端采用手机 H5，推演先满足运输时效、电量安全及资源可用性，再比较成本与等待。成本与等待权重未指定，不能自行确定唯一综合评分。

本节点输出用户任务、业务范围、需求与验收目标；菜单和状态权限设计在 D2，逐模块规则及字段在 D3，逐页面规格在 D4，独立高保真原型在 D5，覆盖审查和冻结准备在 D6。

## 5 角色和三条核心旅程

ROLE-001 平台管理员：组织需求和资源，推演确认，派发和调整任务，监测处理异常，管理成本资产，分析与汇报。

ROLE-002 司机：只处理自身关联任务与必要补能信息，接收或拒绝任务，反馈执行节点与异常，提交完工信息。移动端形态已确认手机H5，地图导航跳转、通知渠道和离线同步策略尚未确认。

其他企业及机构作为业务主体建档；是否开通独立账号留待需求变更。管理员是否细分操作授权与数据范围在D2/D3明确，不能默认所有管理员可跨主体读取全部经营数据。

三条旅程沿用需规并在D2详细建模：

1. 运输补能：需求登记 → 订单 → 核验输入 → 推演 → 比较确认 → 运输/补能计划 → 派单 → H5承接与执行 → 实际补能及节点回传 → 管理员完工确认 → 成本复盘。
2. 风险处置：遥测/规则/司机反馈 → 风险提示 → 核实及关联影响对象 → 处置或重算 → 管理员确认计划变更 → 通知与执行反馈 → 关闭归档。
3. 资源规划：业务及流量数据 → 缺口识别 → 候选点与接电用地条件 → 容量及车辆电池测算 → 多方案比较及版本保存 → 人工审查建议。

任务前规划、途中调整、完成后复盘的组织方式来自外部案例启发，与上述需求保持映射；未将外部案例扩展为新增账号或结算需求。

## 6 核心业务实体和术语

| 实体 | 在本项目中的含义 | 需在后续确认的关系 |
|---|---|---|
| 运输需求 | 委托主体的运量、起讫点和时间要求 | 与订单一对一或一对多尚待确认 |
| 订单 | 需被组织履约的运输业务对象 | 订单拆分、合并与取消条件 |
| 推演运行/候选方案 | 一次输入与约束下的测算版本及结果 | 方案版本、失效条件、确认与重算关系 |
| 运输计划/任务/车次 | 计划组织、派给车和司机的工作、实际往返执行次数 | 不将任务等同单一车次；多趟短倒的拆分与归集待确认 |
| 执行事件 | 接单、开始、装卸、到站、补能、异常、完成等记录 | 司机反馈与设备事件冲突时的核验来源 |
| 运力资源 | 车辆、司机、所属主体、可用时段及补能适配 | 车辆司机绑定、换班和占用规则 |
| 场站/设备 | 补能服务位置及充电桩、换电工位等资源 | 母子站分工、设备排队、功率共享与服务方式 |
| 补能计划/作业 | 预计到站安排与实际充电或换电记录 | 一任务多次补能，换电电池编号及库存关联 |
| 能源资源/协同计划 | 供电边界、绿电储能及分时供需安排 | 计划建议和设备控制相互独立 |
| 告警/处置记录 | 潜在或已确认异常及处理过程 | 风险等级、确认责任和关闭条件 |
| 成本记录/测算 | 预计或实际费用及计算依据 | 单位、税费、分摊与缺项口径 |
| 车辆/电池资产与置换记录 | 归属、租赁、投运、维护、流转及置换证明 | 与运力主档案共用标识，不重复建档 |
| 规划方案 | 候选网络及容量投放的条件测算 | 用地接电核验、审批主体、数据时间区间 |

SOC为荷电状态；电量采用kWh、功率采用kW等业务单位将在D3统一。当前不把“单站32兆瓦”套用所有场站，也不假设换电电池、车辆及接口天然兼容。

## 7 推演、预测与AI的分工

交能推演输入：订单、装卸时间、车辆/司机可用性、载重、道路、SOC与能耗、场站适配和容量、供电边界。用户确认的目标次序是：先满足时效、安全及资源可用性，再对成本和等待形成可比较结果。

以下为后续规则设计建议，尚需D2/D3确认：装卸时间窗、车型通行、补能兼容等作为可行性约束；成本与等待采用并列指标或候选方案比较，不预设数值权重；无可行方案时解释冲突，不自动放松安全余量或时间要求。安全余量、模型参数和权重保留为显式待确认项。

预测计算负责到站、服务、排队及负荷测算，必须区分当前占用、计划到站和预测队列。预测时间窗口、粒度、所需样本及误差目标待确认。

AI负责理解意图、整理条件、调用授权计算能力、引用记录和解释结果；派单与业务变更需要管理员确认。原型对话可以模拟调用，但明确显示示例，不能直接生成无依据的真实路线、功率或成本结论。

## 8 数据与现有系统衔接

八类数据范围按需规§2.4保留：运输业务、车辆运力、交通路网、场站设备、补能业务、能源资源、价格成本、规划资产。

| 接入领域 | 需要确认的基础资料 | 未取得资料前的设计表达 |
|---|---|---|
| 运输订单 | 来源主体、字段、更新和变更机制、样本 | 原型样例与导入交互；不得称外部系统已打通 |
| 车辆 | GPS、SOC、能耗里程、时间戳、车型兼容 | 未接入/人工/延迟等状态完整设计 |
| 场站 | 桩与工位状态、服务时长、库存、电池适配、计费记录 | 充电与换电分别设计，接口能力待核实 |
| 能源 | 接电容量、负荷、分时电价、绿电储能、采集时效 | 可登记的边界与条件测算，控制动作不默认开放 |
| 路网地图 | 坐标、矿区道路、限高限重、通行及路线来源 | 地图与路线来源标识；原型示意不作为真实货车可达路径 |
| 成本 | 电费服务费、司机车辆费用、租赁维保及分摊 | 估算/实际/缺项分别呈现，不用缺失费用凑出完整利润 |
| 规划 | 流量轨迹、候选点、用地接电与投资参数 | 未核实条件可见，方案不替代审批 |

辽粮代码只读参考，没有运行其服务、复用数据库、读取API密钥或连接生产接口。新建方向已明确，无既有系统迁移前提；有历史数据时另确认导入范围。

## 9 验收层次和成功标准

每条需求的验收目标见 requirements.csv，详细验收场景见 acceptance-scenarios.md。本节点只定义可观察的业务结果；不凭空承诺降低百分之多少成本或提高多少出勤率。

设计与原型验收：需求有对应业务、页面和交互；场景可走通；各种数据属性和缺失状态清晰；派单、改派、告警处理等有确认与反馈。

后续开发验收：真实前端/API/数据形成执行闭环；模型使用经过确认的输入与约束；接入时效、预测误差、试点规模、并发及恢复指标在数据与范围确定后量化。该层不由本轮HTML原型替代。

运营效果评估：按统一窗口比较任务按时完成、车辆周转、补能等待、单位成本及告警恢复，先取得真实基线，再约定效果目标。

## 10 需求排序与风险

采用P0/P1标识必要闭环和重要辅助能力，不在缺少工作量、人员和日期时编造RICE分数或容量比例。全量需求均保留设计，排序详见CSV。预测、规划和资产深度依赖真实数据，不因演示可点击就判定模型可投入运行。

主要不确定事项：订单任务车次关系、优化参数、数据源及实际规模、设备和电池兼容、司机反馈核验、成本公式、角色数据边界、预测与性能阈值。原需规QC-01—12逐项登记在open-questions.csv。QC-02的H5形态已解决，通知离线等子项仍开放；QC-06的目标次序已解决，权重与派单规则仍开放；QC-11的新建方向已解决，历史导入条件仍待有资料时核实。

尚未解决的事项按需要决策节点分配负责人类型：业务负责人确认规则和边界，数据负责人确认接入，成本负责人确认核算。没有实际名单时不虚构责任人姓名。

## 11 本轮参考结论

辽粮Planning.vue中的需求带入、条件更改未求解保护、候选比较和运行版本关联，AgentPlanConfirmation.vue中的条件确认，AgentPlanResult.vue中的候选及路线展示，TaskExecution.vue中的事件及异常关联，适合作为交互参考。参考记录含源码位置及哈希，未将其规则直接移植。

其粮食单位、联运方式、供应商发布与报价、装货回单必填、具体数值校验、技术框架及后端接口不成为本项目业务规则。样式仅记录浅色业务面板、表单分组、重点操作和状态的表达，D4再统一设计规范。
