## E2 数据与接口

新增 records 资源类型 planning-projects、planning-solutions，沿用已有 resource/owner/status 索引及 JSON CHECK。不做破坏性建表迁移；既有 planning、deployment 成果仍保留，可在历史抽屉查看。项目关联以 project_id/owner_id 业务约束验证，方案与候选引用必须同主体；单写事务内递增版本并保存命令结果及审计。新方案计算快照不覆盖旧方案；状态与采用元信息允许更新。项目 version 为条件版本，采用 reference_id 属引用元信息，不使同条件其他方案失效；方案自身 version 参与乐观锁。当前参考不能归档；更新项目条件使原方案过期；采用时重新核对资源签名，档案/设备/任务发生改变需要重算。

- GET /api/planner/options?owner_id：当前授权主体候选点、场站及可编辑默认仿真条件。
- GET /api/planner/projects?q：查询有权访问的全部项目（选择器需完整集合）。
- GET /api/planner/projects/:id：项目及方案快照，按版本倒序；前端默认10条/页展示历史。
- GET /api/planner/business?owner_id&start_date&finish_date：订单与未分配需求余量去重，按时窗交集分摊；核验交付按已核验车次时点单列；缺时窗不猜测。
- GET /api/planner/handoff/:id：验证有效方案与推演支持范围，提供主体、规划引用、参数及有依据的首条运输走廊。
- POST /api/commands：planner.create / planner.update / planner.calculate / planner.adopt / planner.archive。写入均需 planning.write，基于会话/CSRF/幂等/事务审计；管理员只读、司机403，越权记录404，版本409，业务条件422。

纯充电模型包含去回程、装卸及单循环能耗分摊的补能时间；电池按80%可用容量核对完整循环，超限则不推荐。设备日需求按能量、运营窗、功率和利用率上限求解。排队为 Erlang C / M/M/c 稳态情景，不含峰时、社会流量和故障；未将等待纳入运输循环，运力建议需在交能推演进一步校核。供电按既有全部装机（包括离线或不适配工位，不能忽略其安装负荷）＋新增装机＋其他负荷，不重复计装机。适配资源与档案总数分列；逐日可用窗口、任务占用、规格、载重、电池、资格与状态逐项筛选。随车电池计数量但不重复计投资；缺工程/设备/车辆报价不输出虚假ROI。覆盖率未做路网覆盖分析显示待分析，道路绕行没有道路依据不输出数字。

## E4 交接与真实性

显式“带入交能推演”传递已校验的规划引用与同主体参数；有多条走廊时带入首条有坐标的走廊及该线路日均运量，提示用户核对。手工项目未知位置保持空白，不偷带示例矿区地址；超出单次推演支持规模/参数时提示调整。进入页不创建运输订单、任务或场景结果，后续由用户自行测算确认派单。

本地使用当前已标仿真的数据库资料创建一个“北区煤运走廊规划（仿真）”，日均运量来自引用区间，首方案待比选，不自动采用。未为了匹配设计图片伪造32辆库存或2400吨/日。设备报价、建设审批与真实运行遥测仍依赖现场资料。此次没有调用真实大模型；既有交能AI入口保持可用。

## E5 验收方法

Node 单元/API测试覆盖计算边界、权限隔离、去重比例、并发版本、幂等、资源过滤、容量未知/不足、分期、过期及归档，并逐行确认隔离库的原业务记录保持。Playwright 可见浏览器检查真实页面到SQLite链路、手机布局及错误；本地真实地图独立检查SDK、底图瓦片、330点道路、完整容器与截图。前后端 build、原171项AC及相关运输/能源/保障回归依照最终报告执行。初始主库备份仅用于追溯，不用它覆盖用户在工作期间发生的新司机操作。
